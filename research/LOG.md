## E1 · 分类协议 A/B：紧凑格式对 token 消耗的影响（2026-08-25）

**动机**：降低单条视频的分类 token 成本。
**设置**：同一批 24 条真实首页视频，同一模型（deepseek-chat），对比新旧两种协议。旧：JSON 输入含 bvid、输出回显 id+类别全称；新：行式输入 `序号|标题|UP主|标签`、输出 `{"r":{"序号":"单字母"}}`。
**结果**：

| 协议 | 输入 tok | 输出 tok | 合计 | 每条 |
|---|---|---|---|---|
| 旧 | 1459 | 370 | 1829 | 76.2 |
| 新 | 1006 | 100 | 1106 | 46.1 |

分类结果两协议基本一致（24 条中 1~2 条边界样本漂移）。
**结论**：−40% 总量、−73% 输出（输出单价最高）。已上线到两个脚本 v1.1.0。
**成本**：≈¥0.005（重算）。

## E2 · 一毛钱能产出多少专业卡片（2026-08-25）

**动机**：回答真实单位经济学，不做纸面推算。
**设置**：清空分类缓存（备份后恢复），专业模式，每 12s 滚动到底模拟连续消费，按 usage 实时累计花费，到 ¥0.10 停止。
**结果**：96 秒，138,068 tok（输入 127,020 / 前缀缓存命中 54,912 / 输出 11,048），90 次请求 0 限流；LLM 分类 1,622 条，判出专业 339 张（页面实际注入 326 张，池内剩 228 条存货）。按现行非峰价重算花费 ≈¥0.17，折合 **≈200 张专业卡/毛，≈5 厘/张**；专业命中率 20.9%。（实验当时按旧价目估 ¥0.108/339 张——token 计数不变，仅单价修正。）
**已知缺陷**：热榜滑块处于 30% 未归零；事后核查热榜池全程 0 条（分区接口 62013 无供给），339 张全部来自个性化流，结论未被污染，但变量控制不合格，复测时应显式归零。
**结论**：逐条送 LLM 的架构下限约 400 tok/张专业卡；要降 2~3 个数量级必须引入本地学生模型。

**结果**：

| 知识区排行榜 | 95 | 46.3% | 13.7% |

## E4 · 362 样本线性模型原型（2026-08-25）

**动机**：验证字符 n-gram 线性模型在本任务上是否有学习信号。
**设置**：E3 的 362 条数据，HashingVectorizer(char 1-3) + NB/LR/LinearSVC，5 折 CV。
**结果**：默认权重下三模型全部退化为多数类预测（pro 任务 F1≈0~0.12，acc≈基准率 71%）。class_weight=balanced + 2^13 维后 LR：pro F1=0.47；neg（正例仅 34）F1≤0.15。学习曲线（n=150/250/362）：pro F1 = 0.33 / 0.37 / 0.43，单调上升。
**结论**：信号真实存在但严重数据饥饿；neg 轴需定向过采样正例。为 E5 缩放实验提供动机。
**成本**：0（复用 E3 标签）。

## E5 · 数据量—效果缩放实验（进行中）

**动机**：得出本场景下"标注量 → 模型效果"的定量关系，确定性价比最优的标注规模；作为后续所有标注预算决策的依据。
**设计**（预注册，跑完不改）：
- 语料：多源结构化采集（每周必看全量 + 全区排行榜 + 全区新投稿深翻页 + 热门深翻页 + 少量个性化流），bvid 去重 + 标题精确去重。
- 金标：deepseek-chat 两轴，分层抽样 ~2 万条；标签质量双审计：①自一致性（500 条打乱重标，报告一致率）②强模型审计（250 条 deepseek-reasoner 重标，报告一致率）。
- 切分：按 UP 主分组 80/10/10（train/val/test），test 冻结后不再触碰。
- 缩放网格：n ∈ {500, 1000, 2000, 5000, 10000, 全量} × 3 种子，从 train 内抽样；模型配置固定为全量数据在 val 上选出的最优线性配置（单变量原则）。
- 天花板对照：hfl/rbt3 双头微调（同一切分）；若 BERT−线性 F1 差 >5pt，追加"银标蒸馏"实验（BERT 高置信标注非金标语料，线性模型 gold+silver 重训）。
- 产物：`results/scaling.jsonl`（每行一个 run）、汇总表回填本节。

**运维事件（2026-08-25）**：每周必看接口以 1~1.5s 间隔连续采集，成功 100 次后触发 -352 风控并持续拒绝。教训：批量采集必须 ≥2.5s 间隔 + 遇 -352/-412 立即弃用该接口族并全局暂停；单接口族单日安全额度按 ≤100 次预算。采集器 v2 已按此重写（3.5s 间隔重试同一接口成功，全程零风控）。另一发现：`newlist` 接口 `pn` 翻页参数无效，每区只能取一页 ~55 条。

**结果**（2026-08-25，语料 17,867 条唯一标题，金标 17,027 条 title 去重后；切分 train=13,467 / val=1,652 / test=1,908，按 UP 分组）：

pro 任务缩放曲线（测试集为 v4-pro 提纯标签，3 种子均值±std）：

| 训练样本数 | F1 | acc |
|---|---|---|
| 500 | 0.360±0.068 | 0.725 |
| 1,000 | 0.464±0.053 | 0.740 |
| 2,000 | 0.525±0.019 | 0.751 |
| 5,000 | 0.578±0.011 | 0.765 |
| 10,000 | 0.587±0.005 | 0.767 |
| 13,467 | 0.606 | 0.771 |

neg 任务（正例率仅 5.1%）：F1 峰值仅 0.18，**当前不可用**——瓶颈是正例数量与标签噪声，不是模型（BERT 也只到 0.22~0.28）。结论：neg 轴暂时保持纯 LLM 判定，待定向补采负能量正例后重训。

主要结论：
1. **缩放律**：pro F1 随数据量单调上升但边际递减（每翻倍约 +2~4pt），13.5k 样本尚未饱和；下一个有价值的数据量级是 5~10 万（需解决供给，见运维事件）。
2. **天花板**：BERT(rbt3) 在同一干净测试集上 F1=0.631 vs 线性 0.606，差距仅 +2.5pt——考虑到标签本身与强模型只有 88% 一致，线性模型已接近该标签质量下的任务天花板，**上更大模型不是当前瓶颈**。
3. **高精度工作点不可行**：线性模型概率分布压缩，P≥0.85 时召回坍缩到 2%——"本地模型独立完成高纯度筛选"路线否决，正确集成方式见 E8。
4. 工程：最终产物 `classifier.js`（int8 量化、与 sklearn 位级对齐、300 样本零判决翻转）；期间修复 JS/Python 两个不一致 bug（sklearn char 分析器的连续空白折叠、JS UTF-16 代理对 vs Python 码点切分——emoji 标题触发）。

## E6 · DeepSeek v4 迁移验证（2026-08-25）

**动机**：旧模型名 deepseek-chat / deepseek-reasoner 已于 2026-07-24 退役（现仍作静默别名可用，随时可能失效）；确认 v4 系列的正确调用方式与成本影响。
**结果**：
- 模型列表实测仅 `deepseek-v4-flash`、`deepseek-v4-pro`、`deepseek-v4-flash-vision-exp`。
- **v4-flash 默认开思考模式**：3 条视频的分类请求产生 144 reasoning token（按输出价计费），若不处理会让分类输出成本涨 ~10 倍。`thinking_effort:"low"` 无效（仍思考）；`thinking:{"type":"disabled"}` 完全关闭（0 reasoning token，输出 13 tok），且与 `response_format: json_object` 兼容。
- 峰谷计价：高峰（UTC 1-4、6-10 点，即北京 9-12 与 14-18 点）价格为非峰 2 倍。批量打标应安排在非峰时段。
- 已迁移：两个用户脚本 v1.2.0（默认模型 v4-flash + 显式关思考 + 峰谷感知计费），打标管线同步迁移（强审计改用 v4-pro）。
**成本**：≈¥0.01（探索性请求）。

## E7 · 标签净化的增益实验（2026-08-25）

**动机**：E5/E6 审计发现 flash 标签有 ~10% 自不一致与对 pro 的系统性偏宽；量化"花钱净化标签"对模型的真实收益。
**设置**：三段净化——① flash 全量重标第二遍取共识（¥1.0，两遍一致率 pro 90.5% / neg 94.4%）；② 两遍分歧 2,250 条交 v4-pro 仲裁（¥21.2，因 v4-pro 思考输出超长导致 JSON 截断，仅 799 条成功）；③ 测试+验证集 3,560 条 v4-pro 整体重标（¥19.8，3,140 条成功，flash 与 v4-pro 在评测集一致率 pro 88.0% / neg 94.3%）。
**关键设计**：对比"噪声标签训练"与"净化标签训练"的两个模型必须在**同一份干净测试集**上评测（曾因导出模型混入全量数据踩过一次评测泄漏，已纠正）。
**结果**（干净测试集，pro 任务）：

| 训练标签 | F1 | P | R |
|---|---|---|---|
| flash 单遍（含噪） | 0.620 | 0.598 | 0.644 |
| 共识+仲裁（净化） | 0.606 | 0.616 | 0.596 |

**结论**：**训练标签净化对模型无增益**（差异在噪声内）——线性模型天然抗随机标签噪声，且仲裁只改动了 ~5% 训练标签。**评测集提纯是三段中唯一高回报的投入**：它把"用有偏尺子量模型"变成可信评测（v1 时代 flash-训-flash-测的 F1=0.658 属于同源噪声抬分）。资金教训：¥21 仲裁 ROI 低，¥20 评测提纯 ROI 高；未来预算优先花在评测集和扩大数据量上。

## E8 · 产品集成策略推导：本地模型作为负例筛子（2026-08-25）

**动机**：E5 表明高阈值高精度不可行，需要重推最优「本地模型 × LLM」协作结构。
**推导**（基于干净测试集实测）：本地模型在默认阈值下 P=0.62 / R=0.60，判正率约 19%。策略「**本地筛负，LLM 只确认本地判正的那 19%**」：最终展示精度 = LLM 级别（本地假阳性被 LLM 拦截），召回损失（漏掉 40% 专业内容）由无限供给补偿（漏判是免费的，多抓几页即可）。
**收益核算**：token 消耗降为逐条全送 LLM 的 ~19%（**5.2×**），叠加已有的结果缓存与 UP 主规则（复刷内容零成本），稳态下预计再乘 3~10×。距离"百分之一"目标：5.2×（本地筛）×已实现的协议压缩 1.65×（E1）≈ 8.6×，其余靠缓存/UP规则/存货不过期的稳态积累达成。
**后续**：集成到用户脚本时按此结构实现；neg 轴暂全量走 LLM。

## E10 · 跨用户泛化：留域测试与语料来源纯度审计（2026-08-25）

**动机**：全部采样与测试都基于单一账号；回答"别的用户信息流分布完全不同（先验不同/领域没见过）时模型行为如何"。

**(a) 留域测试**（模拟"从没见过的领域"：把某分区的排行/新投稿样本全部从训练集剔除，只在该分区上测，与含该域训练的对照组同训练量对比，pro 任务）：

| 留出分区 | n | pro率 | 见过该域 F1 | 没见过该域 F1 | Δ |
|---|---|---|---|---|---|
| 知识 | 149 | 45.6% | 0.904 | 0.631 | −0.27 |
| 科技 | 157 | 35.0% | 0.864 | 0.667 | −0.20 |
| 纪录片 | 124 | 56.5% | 0.903 | 0.412 | −0.49 |
| 美食 | 147 | 8.8% | 0.727 | 0.529 | −0.20 |
| 动物 | 97 | 8.2% | 0.667 | 0.333 | −0.33 |
| 游戏 | 192 | 8.9% | 0.762 | 0.364 | −0.40 |
| 生活 | 255 | 3.9% | 0.513 | 0.290 | −0.22 |
| 舞蹈 | 146 | 6.2% | 0.818 | 0.200 | −0.62 |
| 汽车 | 94 | 34.0% | 0.941 | 0.667 | −0.27 |
| 动画 | 150 | 5.3% | 0.778 | 0.353 | −0.42 |

**结论**：未见领域 F1 平均掉 0.2~0.6，且主要死于**召回坍缩**（纪录片 R=0.30、舞蹈 R=0.11）——即系统性假阴性：整个领域的专业内容被静默过滤，且该错误方向没有 LLM 兜底（只有判正才送 LLM）。这实证确认了跨用户部署的核心风险。

**(b) 语料来源纯度实测**（同一时刻登录态 vs 无 Cookie 拉同一接口对比重合度）：
- 新投稿 newlist：重合 90%（差 1 条为时间漂移）→ **确认全站性**
- 综合热门 popular：登录态 vs 无 Cookie 重合仅 25%，而无 Cookie 两次自比 100% 一致 → **确认热门接口按账号个性化**（语料中 283 条，占 1.6%，有账号偏色）
- 排行榜 / 每周必看：无 Cookie 被 -352 拦截无法裸验；语义上为公开榜单与固定编辑精选（"第N期"清单），推定全站，待用干净浏览器 profile 终验
- 个性化推荐流 rcmd：597 条（3.5%），有意保留作部署分布锚点

**部署设计三道防线**（由 (a) 推导）：
1. **负例审计抽样**：随机抽 2~5% 本地判负样本送 LLM 复核——把不可见的假阴性变成可测量信号，成本极低；
2. **端上自适应**：审计与确认产生的用户本地标签对线性模型做在线增量更新（几行 JS，数据不出端）——模型向该用户的领域分布自动漂移；
3. **分歧率降级**：监控本地-LLM 分歧率，超阈值自动提高送 LLM 比例直至回退全 LLM——最坏情形 = 回到全 LLM 的成本，质量永不劣化。
先验差异（有人专业多/少）只影响成本不影响质量：专业少 → 判正少 → LLM 调用少（更便宜）；成本随价值同向伸缩，方向有利。

## E11 · 端上在线学习闭环仿真：陌生域召回恢复（2026-08-25）

**动机**：验证「覆盖采集 + 用户机器上补充训练」架构能否修复 E10 的陌生域召回坍缩。
**设置**：基础线性模型训练时完全剔除纪录片/舞蹈/动物三域（模拟陌生域用户）；1/3 域内样本冻结为评估集，2/3 作使用流重复 3 轮（近似数周真实曝光）。闭环策略：本地判正→送 LLM 确认；判负→按审计率抽查（冷启动 20%，200 次曝光后降至 5%）；每个 LLM 标签做一次在线逻辑回归更新（lr=0.5，仿真以金标模拟 LLM 回答）。
**结果**（冻结评估集 n=122，pro 率 29%）：

| 曝光数 | R | P | F1 |
|---|---|---|---|
| 0（静态域外模型） | 0.26 | 0.64 | 0.37 |
| 100 | 0.43 | 0.68 | 0.53 |
| 300 | 0.57 | 0.69 | 0.62 |
| 700 | **0.63** | 0.71 | **0.67** |

LLM 调用占曝光的 28%（含冷启动重审计，稳态随模型变准下降）。
**结论**：端上在线学习把陌生域 F1 从 0.37 拉回 0.67——超过全局模型在熟悉分布上的水平（0.61），几百次曝光即收敛，**E10 风险有工程解**。落地要点：只学 LLM 确认过的标签（防自我强化闭环）、delta 限幅与漂移重置、稀疏增量存 localStorage。仿真局限：金标模拟 LLM（真实一致率 88%，信号略噪）；单用户单种子。
**成本**：0（全本地）。

## E17 · 个人兴趣模型：前人研究扫描（2026-08-26）

## E14/E15 · 双轨画像保真度：合成用户回放（2026-08-26）

**设置**：8 个已知兴趣配比的虚拟用户 × 3 种子，每人 1500 事件（60% 兴趣采样 + 40% 随机曝光，兴趣内容 55% 观看/15% 点击），画像引擎为长短期双衰减 + 软主题归属 + 互动加权（interest-model/eval/profile_engine.py）。分类概率一律用**外折预测**（曾因全量重训模型混入回放条目产生泄漏——泄漏版 cos 虚高至 0.75，已纠正）。
**结果**（长期画像 vs 真实配比）：

| 轨道 | 粒度 | cos | top3命中 | 漂移(2/3跟上/800事件内) |
|---|---|---|---|---|
| 轻量轨 n-gram | 48 类 | 0.384 | 0.361 | 25% |
| 轻量轨 n-gram | 13 大类 | 0.490 | 0.604 | 25% |
| 完整轨 嵌入 | 48 类 | 0.736 | 0.889 | 17% |

## E21 · 事件回传静默失效（2026-08-26）

**现象**：反馈称插件从未向 daemon 回传过事件。
**诊断**（真实页面 + daemon 实测）：回传链路本身通（实测 17 条入库），但有两处让失败完全不可见：
1. `fetch` 遇到 HTTP 403 是正常 resolve 而非 reject，代码只挂了 `.catch()` 从不检查 `r.ok` —— **连接码失效时事件被当作发送成功并永久丢弃**，且无任何提示。连接码会在 daemon 数据目录重建时更换（开发期多次发生），用户侧无从察觉。
2. 事件先 `splice` 出队再发送，daemon 未运行时直接蒸发，不重试。
**修复**：检查 `r.ok`；403 判定为配置错误并弹一次明确提示；网络失败则把事件放回队列（上限 1000）并按 5s→60s 指数退避重试；🔗 按钮（已有元素）的提示实时反映连接状态：未启用/已连接/连接码不对/服务未运行已暂存。
**验证**（四种情况）：

| 情况 | 状态 | 事件 | 提示 |
|---|---|---|---|
| 连接码正确 | ok | 16 条入库 | 按钮「已连接」 |
| 连接码错误 | bad | 0 条，不丢进黑洞 | 弹窗提示重填 |
| 服务未运行 | offline | 16 条留在队列 | 按钮「已暂存」 |
| 服务恢复 | ok | 39 条自动补投 | — |

## E23 · 一次性配对：去掉手抄连接码（2026-08-27）

**来源**：Breadcrumb（Leo 的另一个桌面项目，只读本服务的五个 GET）提出——它已把本机服务的启动自动化，只剩"用户把连接码从它的界面手抄进浏览器脚本"这一步无法消化，提议改用 Origin 判定放行。
**决定：不采纳 Origin 判定。** 它把写入权限从"持令牌者"放宽到"任何在 bilibili/youtube 页面里执行的脚本"，包括平台自身加载的第三方脚本、用户装的其他油猴脚本和潜在 XSS。代价由全体用户承担（其中绝大多数从未听说 Breadcrumb），而收益只是省去一次粘贴——不成比例。注：读接口本就不发 CORS 头，页面脚本读不到画像，所以 Origin 放行的暴露面是"污染"而非"泄漏"；即便如此仍不划算。
**采纳的替代方案：一次性配对码**（令牌仍是唯一凭证，安全模型不降级，只是让令牌自己走过去）：
1. 本机程序凭令牌调 `POST /pair/new` 换一个一次性配对码（120 秒有效）——这一步天然只有能读令牌文件的本机程序做得到；
2. 它用浏览器打开 `https://www.bilibili.com/#im-pair=<配对码>`；
3. 脚本发现 fragment 后**先把它从地址栏抹掉**，再调 `POST /pair/exchange` 换令牌；服务端校验配对码有效、未用过、未过期，且 Origin 在白名单；
4. 兑换即作废。令牌全程不显示、不进剪贴板、不留在历史记录。

**过程中发现的真实缺陷**：首轮测试失败且状态自相矛盾（hash 未清、配对码未消费，但事件仍在流通）。原因是**同文档导航**——从 `bilibili.com/` 跳到 `bilibili.com/#im-pair=...` 只改 fragment，浏览器不重新加载页面，脚本不会重跑（旧实例闭包里还留着上一轮的令牌，造成"看起来正常"的假象）。这不只是测试环境问题：用户已开着站点、由本机程序往当前标签页追加配对码，是真实路径。已补 `hashchange` 监听。
**验证**（7 项全过）：无令牌申请 403 / 有令牌申请得 24 字符码 / 非白名单 Origin 兑换 403 / 伪造码 403 / 新标签页配对成功（令牌入库、hash 抹除、34 条事件流通）/ 已开页面追加 hash 同样成功 / 配对码复用 403。
**配套**：新增 `interest-model/API.md` 作为对外契约——声明 `api_version`、只做增量字段、改名或改语义会升版本并提前公告；同时写明 `/emotion_series?cat=gent` 由 valence 阈值定义，不可作为效果证据（见 E22）。
**保留**：E21 的失败重投队列（Breadcrumb 亦希望保留）；🔗 手动填码作为不使用本机程序时的后备。
**成本**：0。

## E24 · 纯本地模式与丢弃带；补货吞吐 2.6×（2026-08-28）

**需求**：①容忍滑条无法彻底关闭 LLM；②低置信视频与其硬判硬展示，不如丢弃（供给无限）；③划出新卡太慢，定位瓶颈。

**瓶颈测量**（真实页面冷启动采样 42s）：专业存货从未攒到 10 条（0~5 震荡，即挖即耗）；一轮 3 页耗 7~9s——B站请求串行化且每次随机延时 300~700ms（占 ~3s）+ LLM 往返 + 轮间固定睡 1.5s；当日信息流专业产出率仅 ~5%（620 条中本地跳过 530）。结论：瓶颈是**专业内容发现吞吐低于滚动消费速度**，不是分类速度。

**丢弃带阈值选择**（外折无泄漏，n=17k）：

| 接受阈值 | 展示精度 | 召回 | 丢弃占比 |
|---|---|---|---|
| 硬切 0.5（原） | 0.552 | 0.575 | 0 |
| ≥0.70，丢弃 0.30~0.70 | **0.706** | 0.281 | 33.7% |
| ≥0.80，丢弃 0.20~0.80 | 0.799 | 0.149 | 55.5% |

## E28 · 架构调查：daemon 还有没有必要（2026-09-08）

**动机**：Breadcrumb 把本项目的兴趣模型整条链路移植成了 TypeScript，去掉了 Python。调查它是怎么做到的，以及本项目能否吸收。全程只读对方仓库。

**它不是靠放弃语义嵌入。** Breadcrumb 用双层：A 层是 `interest_lite.js` 的逐位移植（同样的 8192 维字符 n-gram 哈希、同样的 int8 权重，parity 测试断言 288 个概率与 144 个画像值零容差相等）；B 层照样用语义嵌入 `multilingual-e5-small`，只是那 113 MB 模型是它的知识树本来就要下的，兴趣模型只额外付 32 KB 系数。**这个前提本项目不具备**，照搬「去 Python」会退化成单层。

**但它顺带证明了一条对本项目价值最高的事实。** 它把分类头在 e5-small 上重训后实测与被替换的 bge-small-zh **打平**（topic top1 0.4001 / group 0.5399 / emotion 0.5075，GroupShuffleSplit 按 UP 分组）。而本项目 `app.py:102,114` 同时加载 **两个** SentenceTransformer——bge-small-zh 给 B站、paraphrase-multilingual-MiniLM 给 YouTube——外加 torch，这正是 600 MB 首次下载的来源。**一个多语言 e5-small 有可能同时顶掉两个**，配合 ONNX 运行时替掉 torch，首次下载有望降到 120-150 MB，打包体积（当前 219-341 MB）同步缩水。

**浏览器端推理已被对方验证可行**：`apps/web/src/shims/embedding/embeddingWorker.ts` 用 `pipeline("feature-extraction", MODEL_ID, {dtype:"q8", device:"wasm"})`，模型存进 Cache API 跨会话复用、命中后完全离线加载，且与桌面原生向量余弦 ≥ 0.995。

**daemon 的最后一个存在理由已消失**：Breadcrumb 源码中 21456 一处不剩，`interest_service.rs` 与所有启动 Python 的代码均已删除。daemon 此后只为本项目自己的仪表盘服务，而仪表盘可以由用户脚本在页面上渲染。

**已修的实缺陷**：对方在移植 `profileEngine` 时标注了负 dwell 会产生负权重。回查确认 `app.py:206` 与 `interest_lite.js:74` 两侧都有，根因是 user.js 用 `Date.now()` 累计观看时长、时钟回跳使差值为负；dwell=-3600 时权重为 -55，把该内容的整个主题分布从画像里减掉且无任何报错。三处已修（两个 user.js 改单调时钟，两个消费端钳位），实测注入负 dwell 后画像负分量为 0。

**尚可吸收、未做**：events 表加 `classifier` 列 + 后台重分类（嵌入模型加载失败时的历史事件目前永远是废数据）；用户脚本的持久化事件队列（当前队列纯内存，关页面即丢，403 也直接丢弃）；`UNIQUE(ts,vid,etype)` 去重索引；训练脚本的两处路径缺陷（写死 `/tmp`、读未压缩的 `corpus.jsonl` 而实际是 `.gz`）。

**成本**：0。

## E29 · 浏览器端嵌入推理实测与选型复核（2026-09-09）

**动机**：E28 提出纯浏览器方案，需先回答「WASM 比原生慢多少」，再确认所选模型是否最优。脚本 `pipeline/embbench/`（真实浏览器 + 本项目 corpus 前 64 条标题）。

**实测**（`Xenova/multilingual-e5-small` q8，Chrome 152，本机 RTX 3060）：

| 后端 | 模型加载 | batch 1 | batch 8 | batch 32 |
|---|---|---|---|---|
| **WASM/q8** | 1.2s | **21 ms/条** | **21 ms/条** | 37 ms/条 |
| WebGPU/q8 | 1.2s | 235 ms/条 | 50 ms/条 | 45 ms/条 |
| WebGPU/fp16 | — | 显卡不支持 | | |

正确性校验随每轮跑：两个后端对同两条文本的余弦为 0.8072 / 0.8085、模长均为 1、每批实际条数已回报核对。

**三条与直觉相反的结论**：
1. **WASM 比 WebGPU 快一个数量级**（21ms 对 235ms）。小模型 + 短文本时 GPU 的传输与启动开销盖过算力收益，这与公开评测一致；本机是真实独显而非软件模拟。
2. **批量越大越慢**（21ms → 37ms）。单线程 WASM 无并行收益，长标题拖累整批。最优是小批量甚至逐条，与 LLM 分类那边攒大批的策略相反。
3. 因此 **WASM 多线程需要 COOP/COEP 响应头、而用户脚本在 B站页面上设不了** 这条限制不构成阻碍——单线程已经够快。

**换算**：按 daemon 实测每日曝光中位 42 条计，一天的量 0.9 秒；现有全部历史 4,702 条约 1 分 39 秒。后台补算不构成问题。对照 Breadcrumb 桌面版 Rust 原生路径自述约 100ms/条，**浏览器 WASM 反而更快**。

**踩坑记录**：首轮基准的 batch 8/32 数字虚高数十倍，原因是语料通过 `execute_script` 注入发生在模块执行之后，实际只嵌入了 1 条却按 8/32 去除。改为页面内 `fetch("./titles.json")`，并让每轮回报实际条数。**基准脚本必须自带正确性校验与样本数回报**，否则会得到一个看着漂亮的假数字。

**选型复核：速度已非瓶颈，真正的成本是首次下载，而当前选择在这一维上不是最优。**

实测浏览器缓存后的真实首次下载约 **150 MB**：模型 113 MB + 分词器 22 MB（25 万词表撑起来的）+ ONNX 运行时 16 MB。据此复核候选：

| 方向 | 对下载量的影响 | 判断 |
|---|---|---|
| **词表裁剪至中英** | 公开做法可减约 60%，且**同时缩小模型与分词器** | 最值得做，与选哪个模型正交 |
| **granite-embedding-97m-multilingual-r2** | 97M 参数，小于 e5-small 的 118M，MTEB 60.3 且「领先 100M 以下次优开源模型 9 分以上」 | 值得与 e5-small 在本项目语料上对测 |
| 静态嵌入 potion-multilingual-128M | **不减小**（128M 参数即 128MB 查找表），只提速 | 对本项目无用：速度已够，缺的是体积 |
| 任务专用蒸馏 | 潜在最小，可能只需数十 MB | `TOPICS.md` 已列为改进路径，属独立课题 |

**结论**：浏览器端推理在性能上没有障碍，方案可行；但把 `multilingual-e5-small` 直接当作最终选择为时过早——在承诺架构前应先测词表裁剪与 granite-97m，二者都直接作用于唯一的真实成本。

**成本**：0。

## E30 · 嵌入模型选型实测：一个 e5-small 同时打赢现用的两个（2026-09-09）

**动机**：E28/E29 提出用单一多语言模型替掉现在的双模型（bge-small-zh 给 B站、MiniLM 给 YouTube），并复核 granite-107m 是否更优。脚本 `pipeline/embed_compare.py`，四个候选跑**同一份语料、同一个逻辑回归头、同一份按 UP 分组的冻结切分**，测试集为 test ∩ v4pro_eval 的 1,692 条（从未参与训练，正例率 28.8%）。

| 候选 | 维度 | 准确率 | F1 | 精确率 | 召回 | 说明 |
|---|---|---|---|---|---|---|
| **intfloat/multilingual-e5-small** | 384 | **0.7949** | **0.6871** | 0.6125 | 0.7823 | 本次最优 |
| BAAI/bge-small-zh-v1.5 | 512 | 0.7872 | 0.6853 | 0.5967 | 0.8049 | 现用，B站侧 |
| ibm-granite/granite-embedding-107m | 384 | 0.7571 | 0.6226 | 0.5631 | 0.6961 | MTEB 榜上领先 |
| paraphrase-multilingual-MiniLM-L12-v2 | 384 | 0.7488 | 0.6282 | 0.5473 | 0.7372 | 现用，YouTube 侧 |

**结论一：可以用一个模型替掉两个，且两侧都不降。** e5-small 对中文专用的 bge 是 0.7949 对 0.7872、F1 0.6871 对 0.6853，**略胜**而非持平；对现用的 YouTube 侧 MiniLM 则是明显胜出（+4.6 个百分点准确率、+5.9 个 F1）。这独立复现并略微超出了 Breadcrumb 声称的「与被替换的中文专用模型打平」。

**结论二：MTEB 排名不迁移到本任务。** granite-107m 在 MTEB 多语言榜上「领先 100M 以下次优开源模型 9 分以上」，在本任务上却比现用的 bge 低 3 个百分点准确率、6 个 F1。**选型必须在自己的语料上测**，公开榜单只能用来缩小候选范围。

**结论三：嵌入路线确实优于本地模型。** F1 0.687 高于 E5 的线性模型 0.606 与 BERT(rbt3) 天花板 0.631。云端复核的价值有独立证据。

**口径说明**：表中不列 HF 缓存体积，因为缓存含 pytorch/onnx/openvino 多份权重，不等于部署体积。真实部署体积见 E29 的浏览器实测：e5-small q8 首次下载约 150 MB（模型 113 + 分词器 22 + 运行时 16）。

**词表裁剪的范围（Leo 定）**：不做激进裁剪。本项目两份语料中「仅含汉字/拉丁」的标题占 99.2%（B站）与 99.7%（YouTube），但两份语料**都采自单一账号的信息流**，反映的是采集者的语言偏好，不能代表国际用户；裁掉的语种在用户侧表现为标题被切成未知 token、分类静默退化。后续测量应产出「覆盖范围 → 体积」的曲线而非二选一，并可考虑两个脚本用不同档位——B站侧用户以中文为主，YouTube 侧需要广覆盖。

**成本**：0。

## E31 · 复核 E30 方案：q8 无损，但嵌入模型本身可能是多余的（2026-09-09）

**动机**：E30 结论「换单一 e5-small」有两个未验证的假设：精度用 fp32 测而部署用 q8；以及「兴趣模型需要嵌入模型」这个前提本身从未被质疑。

**其一，q8 量化无损，方案这一半站得住**（`pipeline/quant_check.py`，同切分同分类头）：

| 精度 | 准确率 | F1 | 精确率 | 召回 |
|---|---|---|---|---|
| fp32 | 0.7949 | 0.6871 | 0.6125 | 0.7823 |
| **q8** | 0.7896 | 0.6844 | 0.6022 | 0.7926 |

向量余弦 0.9965，准确率差 0.5 个百分点、F1 差 0.3 个——**小于同模型跑两次的波动**。部署 q8 不需要顾虑。

**其二，一个被忽略的前提：嵌入分类器存在的意义，只是去逼近 LLM 已经会做的事。** `topics.jsonl.gz` 与 `emotions.jsonl.gz` 本就是 deepseek-v4-flash 标的；而用户脚本**已经在把同一批标题发给 LLM 做四分类**。让同一次调用顺带给出主题与情绪，即可省掉整个嵌入模型。

实测（`pipeline/llm_topic_probe.py`，qwen-flash，400 条，金标为上述 flash 标签）：

| 指标 | LLM 顺带标注 | 嵌入分类器（Breadcrumb 在本项目语料上重训） |
|---|---|---|
| 主题 top1 | 0.3975 | 0.4001 |
| 主题分组 | **0.595** | 0.5399 |
| 情绪 top1 | 0.500 | 0.5075 |
| 首次下载 | **0** | 约 150 MB |
| 成本 | ¥0.0178/千条（独立调用） | — |

**两者精度实质相同，分组还更高，而额外成本接近于零。** 独立调用即 ¥0.0178/千条，与现有四分类调用的 ¥0.0175 基本相同，因为输入 token 占大头（42.8 对 7.6）而那些输入本来就在发；若并入现有调用，边际成本只有约 7.6 个输出 token，即 +¥0.011/千条。

**因此 E28 的路线图需要修正。** 原路线是「单模型替双模型 → 浏览器端推理 → daemon 退役」，其中第一步收益确定。但对**已配置 LLM Key 的用户**，更优解是根本不加载嵌入模型：主题与情绪随四分类一并返回，零下载、零额外延迟、精度不降。嵌入模型退化为**无 Key 用户的可选增强**，而非必需组件。

**尚未验证、决定该走哪条路的两点**：
1. **覆盖率**。线上路由只把本地模型拿不准的中间带送云端，曝光事件多数不过 LLM。兴趣画像需要全量事件的标签，而非仅中间带。要么放宽路由（成本按上表估算仍极低），要么未送云端的部分继续用本地 n-gram，两者精度不一致会污染画像聚合。
2. **隐私口径变化**。当前只有不确定的少数标题发往 LLM 服务商；改为全量会显著扩大发送范围。这与项目立场直接相关，需 Leo 定夺，不应由实现者默认。

**成本**：¥0.007（qwen-flash 400 条两轮）。
